# API conventions

## Scope

These conventions apply to the Socrat HTTP API and worker boundary from M1 onward. The OpenAPI document generated by FastAPI is the executable interface description in non-production environments.

## Paths and versions

- Product endpoints use `/api/v1`; health and operational endpoints use `/api/health` and `/api/metrics`.
- Breaking product-contract changes require a new major path. Additive fields remain backward compatible.
- Resource identifiers are opaque UUID strings. A caller must never infer ownership from an identifier.

## Authentication and authorization

- Browser sessions are opaque, random, server-side records. Only a SHA-256 token digest is persisted.
- Cookies are `HttpOnly`, `SameSite=Lax`, path `/`, and `Secure` in staging/production.
- State-changing requests require an exact allowed `Origin` and a per-session CSRF token.
- Authorization is performed on every owned-resource query. Cross-owner reads return `404` to avoid resource enumeration.
- Local developer login is absent unless explicitly enabled, and settings reject it for staging/production.

## Requests and responses

- JSON inputs reject unknown fields. Strings are bounded and normalized only where the contract explicitly permits it.
- Errors have the shape `{ "error": { "code": "stable_machine_code", "request_id": "uuid" } }` and never echo submitted secrets or profile values.
- All responses carry `X-Request-ID`, `Cache-Control: no-store`, and `X-Content-Type-Options: nosniff`.
- `422` means a structurally or semantically invalid request; `401` means no valid session; `403` means the authenticated/request boundary rejected the action; `404` covers missing or concealed resources.

## Transactions and events

- A domain mutation, its audit record, and its outbox event commit in one database transaction.
- Outbox handlers are idempotent. An event ID is processed at most once per consumer.
- Logs and metric labels use route templates, stable codes, and opaque request IDs. They never include profile values, credentials, cookies, raw code, or event payloads.

## Schema changes

- Alembic migrations are reviewed and run as a release step, never at application startup.
- Prefer expand, backfill, verify, switch, and contract. A down migration is useful in development but production rollback should normally deploy the previous compatible application while retaining expanded schema.
- Every release rehearses the migration on a current-size staging copy and proves backup restoration into an isolated database.
